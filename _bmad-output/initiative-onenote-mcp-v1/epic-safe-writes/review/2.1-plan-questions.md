## A latent bug found on the way (D4)

The store and the writer parse settings.json differently, and one case contradicts AD-6:

- An **exact** duplicate key inside `protectedSections` is flagged "duplicate-only" by the store (`SettingsStore.cs:204-209`). That is meant to let `grant --revoke` run (AD-6).
- The writer then loads the file with duplicates forbidden (`SettingsWriter.cs:158`) and throws `SettingsInvalid`. So revoke fails on exactly the file it is supposed to repair.
- An exact duplicate anywhere else (e.g. `timeouts` twice): the store says Ok (last wins), and every save fails.

You only get exact duplicates by hand-editing. AD-21 covers case-only duplicates and says nothing about exact ones. Neither direction is specified, and no test covers it.

:::question
**D4: what should 2.1 do about exact duplicate keys?**
- (a) Keep today's behaviour, with the difference made explicit in the shared helper (`Options(allowDuplicateProperties)`). Route the fix to entry 6, which owns revoke, and the rule to entry 3's spine amendments.
- (b) Fix it here: revoke's load accepts duplicates (last wins), so revoke repairs the file. This is a second behaviour change in 2.1.
- (c) Fix it here: the store reports an exact duplicate anywhere as plainly Invalid, not duplicate-only. Revoke is then refused up front with a clear reason, not a confusing write failure. This is also a behaviour change.

Recommended: (a)
:::
