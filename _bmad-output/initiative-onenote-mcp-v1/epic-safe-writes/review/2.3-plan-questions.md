# 2.3 plan: questions before the spine amendment

The plan is beside this folder (`../story-spine-amendments-from-the-page-write-probes-plan.md`). Most amendments follow straight from the findings and need no choice. These eight do. The plan runs about 1,700 tokens, a little over the 1,600 guide; I'd keep it whole, since a half-amended spine would leave entries 4 and 5 building on old rules.

:::question
**Q1: the cloud-image refusal in AD-7's PageWrite validate.** Resending an Outline that holds an undownloaded image kept the image (constraint 6). That was one image in one run. If an image ever were dropped, the journal couldn't bring it back: it has no binary to save.
- (a) Drop the refusal. The new read-back step checks that each image in the sent Outlines is still there, and reports a lost one as a warning.
- (b) Keep the refusal as caution until more evidence exists.
- (c) Drop it with no extra check.

Recommended: (a)
:::

:::question
**Q2: hash exclusions in AD-17.** Two quirks would make every read-then-write of a page fail `StaleWrite`. Spike 1.15 saw `Column/@width` alternate on one real page, and story 1.17 saw `InsertedFile/@pathCache` change on every read. Spike 2.2 reproduced neither: 20 reads each, one value. `pathCache` is a local cache path, not content. An unlocked width is auto-sized by OneNote, which replaced the 80 and 120 sent on create with 37.11.
- (a) Exclude `pathCache` and unlocked `Column/@width` (no `isLocked="true"`) from `ElementHash`. A concurrent width-only change then goes undetected.
- (b) Exclude `pathCache` only; keep width in the hash until it recurs.
- (c) Exclude neither, and wait for evidence.

Recommended: (a)
:::

:::question
**Q3: dialog order for a write in a protected section.** It needs both the notebook's write grant and the section's read grant (decision 3).
- (a) Write grant first, then the read grant, both in AD-7 step 1 before the lock is taken. A decline at either stops the write.
- (b) Read grant first, then the write grant.
- (c) One combined dialog. Elicitation can't show fields conditionally, so it would ask for both names every time.

Recommended: (a)
:::

:::question
**Q4: does a `once` read grant cover a write?** AD-21 checks the 5-minute window when a call starts, so a call that starts inside it completes. A write's step-3 read and its read-back sit inside one call.
- (a) Yes. A write that starts inside the window completes, read-back included, as a read does today.
- (b) No. Writes need an `hours` or `untilRevoked` grant.

Recommended: (a)
:::

:::question
**Q5: does `create_page` in a protected section need the read grant?** It reads only the hierarchy and takes no snapshot, so it reveals nothing inside the section.
- (a) Yes. One rule for every write into a protected section, as decision 3 is worded.
- (b) No. The write grant alone is enough, because nothing is read.

Recommended: (a). Pushing back on (b): the new page's ID and title then sit in a section the model can't read, and a later read of the page it made raises the dialog anyway.
:::

:::question
**Q6: restoring a protected journal entry when its section is locked or gone.** Decision 3b allows restore only into the same protected section, never into `Recovered`.
- (a) Locked: `SectionLocked`, retryable after the user unlocks. Gone, or no longer protected: `ObjectNotFound`, with a `userAction` naming the entry file, which stays for its 30 days.
- (b) As (a), but an unprotected section at the same path is allowed.

Recommended: (a)
:::

:::question
**Q7: an exact duplicate key in `protectedSections{}` or `notebooks{}`.** Today the store treats it like a case-only duplicate, but `grant --revoke` then refuses to touch the file, so it can never be fixed (deferred-work, from 2.1).
- (a) Exact and case-only duplicates are treated alike: the file is `SettingsInvalid`, and `grant --revoke` runs anyway and removes every entry that matches the key.
- (b) An exact duplicate is a hard error that the user edits out by hand.

Recommended: (a)
:::

:::question
**Q8: what `delete_page_content` may target.** Only deleting an Outline was probed; image and ink come from the API docs. Today `elementHashes` covers only Outlines and OEs (`PageBasis.cs:16`), so a page-level image has no hash to check.
- (a) v1 deletes Outlines only. Other targets get `InvalidArgument`, plus a Deferred row.
- (b) Any page-level object. `elementHashes` adds every direct child of `one:Page` that has an `objectID` (a read contract change), and entry 10 probes image and ink.

Recommended: (a)
:::
