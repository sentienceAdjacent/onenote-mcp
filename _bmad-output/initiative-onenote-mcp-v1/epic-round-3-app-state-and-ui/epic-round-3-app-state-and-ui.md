# Round 3: app state and UI

## Description

This epic adds the `AppState` class's pipeline and the rest of the COM surface:
- `OpenHierarchy` on an existing notebook, `CloseNotebook`, `SyncHierarchy` and `SetFilingLocation`;
- the user-visible calls `NavigateToUrl`, `QuickFiling` and `Windows`, called only when the user explicitly asks (AD-11). `NavigateTo` shipped in epic 1 as `navigate_to` (story 1.21); this epic moves it onto the `AppState` pipeline and lets it target a chosen window;
- events, if they can be built and delivered;
- the remaining Application members (`COMAddIns`, `LanguageSettings`, the `Dummy1` slot): each gets a tool or a dated Decision not to expose it.

It opens with a probe spike for the COM behaviours no earlier spike settled, then amends the spine, and ships as a release with the skill and README updated. As the last epic, it also checks the initiative's Done when 4 across all five epics.

## Outcome

Claude can drive OneNote's app state when the user asks ("open that notebook", "close it", "sync it now", "show me this link", "what page am I on?"), without taking focus or changing what the user sees unasked. Every Application method has a released tool or a dated Decision.

## Requirements

- **A1 (R9) — The `AppState` pipeline.** Every `AppState` tool runs AD-7's pipeline as entry 2 sets it for this class: no grant (AD-7), the write lock for the calls that change the notebook list or OneNote's options, the 120 s deadline, and `outcomeUnknown` on the failures AD-7 step 7 lists, never retried (AD-3); entry 2 says whether a call that changes nothing, such as `get_windows`, can be `outcomeUnknown` at all. `navigate_to` moves onto it. Each tool's description says what it changes; the user-visible ones carry "user-visible" (AD-11). The skill calls every `AppState` tool only when the user asks (Assumption). (AD-7 `AppState`, AD-11)
- **A2 (R9) — `sync_hierarchy`.** `SyncHierarchy` on a notebook, section group, section or page. The result says the sync was requested, not that it finished: the call returns at once (spike 1.15) and OneNote gives no way to see a sync complete (OneMore). (AD-7 `AppState`)
- **A3 (R9) — `close_notebook`.** `CloseNotebook` on a notebook ID, anything else refused before COM, with the `force` rule Q1 sets and the grant rule Q2 sets. It drops the notebook's pages from the search cache, a new rule entry 2 adds to AD-12, which today drops only a written page. Its result gives the notebook's name and path, so it can be reopened, and warns that every ID in the notebook changes when it reopens; grants survive, because they are keyed by path (AD-6). A close that OneNote holds behind its "syncing changes" dialog surfaces as `Timeout` with `outcomeUnknown` (5.1 constraint 11), and the `userAction` says to check OneNote. (AD-7 `AppState`)
- **A4 (R9) — `open_notebook`.** `OpenHierarchy` on an existing path, never creating anything: `cftNone`, with the path checked to exist under the write lock (AD-7). It opens what Q3 allows, refuses before COM a package (epic 3's `open_package` opens those), a missing path, and a folder that isn't a notebook (no `.onetoc2`), because `OpenHierarchy` makes a notebook in any existing folder when asked to create (5.1 constraint 18) and entry 1 checks what `cftNone` does there, and returns the notebook's ID and name. A notebook that is already open returns its current ID from the hierarchy without calling COM, because OneMore reports that OneNote navigates to an already-open notebook, though spike 1 saw no focus change (Assumption). It gives no grant, though an existing grant for the same path applies (AD-6). What it opens follows AD-21 as Q3 and epic 3's Q11 set. A cloud notebook can take about 90 s to fill, and the result says so. (AD-7 `AppState`, AD-21)
- **A5 (R9) — `set_filing_location`.** `SetFilingLocation` for where Outlook items, web notes and printouts land, shipped only if Q8 keeps it; otherwise a dated Decision. There is no getter, so the tool can't report or restore the previous value. (AD-7 `AppState`)
- **A6 (R9) — Windows.** A `get_windows` tool lists OneNote's windows: handle, active state, the notebook, section group, section and page each shows, and its view. Q5 sets whether reading them is user-visible. `navigate_to` takes an optional window. Q4 sets which window changes are exposed. Every `Window` wrapper is released explicitly (OneMore row 10). (AD-11, AD-2)
- **A7 (R9) — `navigate_to_url`.** A user-visible `NavigateToUrl` for the URLs Q6 allows, checked before COM, with the new-window rule Q7 sets for it and `navigate_to`, and the optional window from A6. A repeated call inside the window entry 1 measures gets a `userAction` to wait. Because OneNote reports success even for a link to a missing page, the tool reads the window's current page afterwards and warns if it isn't the link's page. That read needs Q5 (a), or an AD-11 exception entry 2 writes, since AD-11 says no use case calls the `Windows` tools internally. (AD-11)
- **A8 (R9) — `quick_filing`.** A user-visible location picker built on `QuickFiling`, shipped only if entry 1 shows its callback works from our process and Q9 keeps it; otherwise a dated Decision. The wait for the user doesn't count against the pipeline deadline, and the result gives the chosen ID or says the user cancelled. (AD-11)
- **A9 (R9) — Events.** `OnHierarchyChange` and `OnNavigate` either ship as notifications the client acts on, or a dated Decision records why not (Q10).
- **A10 (R9) — Coverage.** Every `IApplication` member, slots 7 to 35 of `src/OneNoteMcp.Com/Interop/IApplication.cs`, has a released tool in one of the five epics or a dated Decision recording why it isn't exposed (the initiative's Done when 4). Entry 2 writes the table; entry 10 checks it against the released tools.

## Done when

1. `sync_hierarchy`, `close_notebook` and `open_notebook` work against real OneNote through the `AppState` pipeline, and `navigate_to` runs on it too. A throwaway notebook closed and reopened by path keeps its grant.
2. `navigate_to`, `navigate_to_url`, and `quick_filing` and window changes where they ship, say "user-visible" in their descriptions. The skill calls them only when the user asks, and no use case calls them internally. `get_windows` reports the page each window shows.
3. Events ship as notifications, or a dated Decision records why they don't.
4. Every OneNote Application member has a released tool, or a dated Decision recording why it isn't exposed, checked across all five epics.
5. It ships as a GitHub release through the epic 1 pipeline, with the skill and README updated.

## Boundaries

This epic owns:
- the `AppState` pipeline, and moving `navigate_to` onto it;
- `OpenHierarchy` on an existing path, `CloseNotebook`, `SyncHierarchy`, `SetFilingLocation`, `NavigateToUrl`, `QuickFiling`, `Windows` and any event sink, on the port and both gateways;
- these tools, the skill and README sections that cover them, and the initiative's coverage table.

Out of scope: anything that writes content; `OpenHierarchy` creating a section, section group or notebook (epic 5); `open_package` (epic 3), though this epic's `close_notebook` closes what it opened; starting, closing or restarting OneNote itself, which stays forbidden (AD-3).

## Notes

- **Needs Phill** (autonomous inception, 2026-11-12). Each question has options and a recommendation; the entries they touch say so.
  - **Q1 — Closing a notebook with changes OneNote can't sync yet.** `CloseNotebook` takes `force`, which closes "even if there are changes in the notebook that OneNote cannot sync before closing" (Microsoft). Options: (a) never pass `force`; if OneNote refuses, return the error with a `userAction` to let it sync, or to close the notebook in OneNote; (b) a `force` argument that the user must confirm in an elicitation dialog naming the notebook; (c) a `force` argument with no extra check. Recommendation: (a). Losing unsynced changes is the one way this epic could lose content, and nothing in the journal would bring them back. Without `force`, OneNote may not refuse at all: in 5.1 a jammed cloud notebook's close hung behind the "syncing changes" dialog, needed Cancel and a retry, and OneNote moved the unsynced sections to Misplaced Sections (5.1, Failure modes). Our call would end in `Timeout`; entry 1 probes it.
  - **Q2 — Does closing or opening a notebook need a grant?** AD-7 gives `AppState` no grant. Options: (a) no grant, as AD-7 says; the descriptions say what the tools change, and the skill calls them only when the user asks; (b) `close_notebook` needs the notebook's write grant; (c) an elicitation confirmation for every close. Recommendation: (a). With `force` off (Q1), a close syncs before it closes, reopening by path brings the notebook back, and its grants survive because they are keyed by path. The one known risk, a close stuck behind a sync jam (Q1), is one a grant wouldn't prevent. (b) would stop a user closing a notebook they never meant to write to.
  - **Q3 — What `open_notebook` opens, and whether AD-21 treats it as protected.** `OpenHierarchy` opens a notebook folder or a `.one` section file. An opened `.one` carries no `encrypted` marker, and a backup or export of a protected section is plaintext (5.1 constraint 17). Options: (a) notebooks only: a local folder path, plus a OneDrive URL if entry 1 shows one works, refusing a `.one` and a `.onepkg` before COM; epic 3's Q11 rule applies by path (a notebook under an export root or the backup folder counts as protected); (b) notebooks and `.one` section files, with every opened `.one` counting as protected under AD-21 and needing a read grant; (c) any path `OpenHierarchy` takes, with only Q11's rule. Recommendation: (a). It covers "open that notebook", and it keeps loose section files, the backup and export route, out of the model's reach.
  - **Q4 — Which window changes are exposed.** A `Window` can be activated, docked, switched to full-page view or made a quick-note window, and can navigate. Options: (a) `get_windows`, plus an optional window on `navigate_to` and `navigate_to_url`; `Active`, `DockedLocation`, `FullPageView`, `SideNote` and `SetDockedLocation` get a dated Decision not to expose them; (b) also expose each setter as a user-visible tool; (c) `get_windows` only. Recommendation: (a). Choosing the window fixes the known problem of the API targeting the first window (OneMore row 14). The setters only rearrange the user's screen, and OneMore never sets them.
  - **Q5 — Is reading the windows user-visible?** AD-11 lists `Windows` as user-visible, but reading a window's current page may change nothing the user sees. Options: (a) if entry 1 shows the read changes neither focus nor the view, `get_windows` is an ordinary `AppState` read: the skill may call it when the user refers to what they're looking at ("this page", "the page I'm on"), and AD-11 lists only window changes as user-visible; (b) keep AD-11 as written: `get_windows` is user-visible and called only when the user explicitly asks about windows. Recommendation: (a). "Summarise the page I'm on" is the most useful thing this epic enables. It does tell the model which page is open, which is why the skill calls it only when the user refers to it.
  - **Q6 — Which URLs `navigate_to_url` accepts.** For any link that isn't a OneNote link, OneNote shows a security dialog, then tries to open it and returns `hrObjectDoesNotExist` (Microsoft). Options: (a) `onenote:` links only, anything else refused with `InvalidArgument` before COM; (b) also the OneNote web links `get_web_hyperlink_to_object` returns, if entry 1 shows the desktop app opens them without a dialog; (c) any URL. Recommendation: (a). The links people follow are the `onenote:` links in their pages, and (c) would let the model raise a dialog and open arbitrary links.
  - **Q7 — New windows.** `NavigateTo` and `NavigateToUrl` can open a new window. Options: (a) never: both tools pass `fNewWindow=false`, as story 1.21 decided for `navigate_to`; (b) an optional `newWindow` argument on both. Recommendation: (a). OneMore needs a 1.5 s settle after each new window, and a refused new-window request can still leave a stray window. The window argument (Q4) covers showing something in a second window.
  - **Q8 — Expose `SetFilingLocation`?** It sets where Outlook's Send to OneNote, Internet Explorer web notes and printouts land. No method reads the current setting. Options: (a) expose `set_filing_location`; the skill calls it only when the user asks, and the result says the old value can't be read or restored; (b) a dated Decision not to expose it. Recommendation: (b). It changes a lasting OneNote option that the server can't read or undo, one of its targets is Internet Explorer, and the user can set it in OneNote's options in seconds. Testing it would also overwrite Phill's own setting. If (b), entry 8 is dropped.
  - **Q9 — Build `quick_filing`?** `QuickFiling` shows OneNote's own picker for a notebook, section or page, and reports the choice through a callback object our process implements. Options: (a) build it as a user-visible location picker if entry 1 shows the callback works from our STA thread; otherwise a dated Decision; (b) a dated Decision now: the model can ask where in chat. Recommendation: (a). Choosing a section from OneNote's own tree is a better answer to "where should I put this?" than typing names. The evidence that it can work: OneMore receives this callback across processes, from `dllhost.exe`, and a read-only registry query on this machine (2026-11-12) shows the callback interface registered with the same type-library marshaler as `IApplication`, which our early binding already goes through (an inference for an STA client, not tested). If (b), or the probe fails, entry 9 is dropped.
  - **Q10 — Events.** Microsoft: "Events cannot currently be added in managed code." OneMore subscribes to none and polls the current page every 1.25 s instead. In Claude Code, the only route for a server to push an event to the model is channels: a research preview, enabled per session with `--channels`, needing a development flag for a server that isn't on the allowlist. Options: (a) entry 1 probes a managed sink; if it works, ship `OnNavigate` and `OnHierarchyChange` as channel events (an extra story after entry 9); (b) entry 1 probes a sink, nothing ships, and a working sink becomes a Deferred row (for example to clear the search cache); (c) no probe: entry 2 records a dated Decision now, citing the above, with a Deferred row to revisit when channels leave the preview. Recommendation: (c). Nothing would ship either way, and `get_windows` answers "what page am I on?" when asked.
  - **Q11 — `COMAddIns` and `LanguageSettings`.** `COMAddIns` lists the COM add-ins available to OneNote. `LanguageSettings` gives access to OneNote's common language settings, and Microsoft documents nothing more. Options: (a) a dated Decision not to expose either; (b) a read-only tool listing the add-ins and whether each is loaded. Recommendation: (a). Neither helps a user work with their notes.
