# Round 3: app state and UI

## Description

This epic adds the `AppState` class's pipeline and the rest of the COM surface:
- `OpenHierarchy` on an existing notebook, `CloseNotebook`, `SyncHierarchy` and `SetFilingLocation`;
- the user-visible calls `NavigateToUrl`, `QuickFiling` and `Windows`, called only when the user explicitly asks (AD-11). `NavigateTo` shipped in epic 1 as `navigate_to` (story 1.21); this epic moves it onto the `AppState` pipeline and lets it target a chosen window;
- events, if they can be built and delivered;
- the remaining Application members (`COMAddIns`, `LanguageSettings`, the `Dummy1` slot): each gets a tool or a dated Decision not to expose it.

It opens with three probe spikes for the COM behaviours no earlier spike settled, then amends the spine, and ships as a release with the skill and README updated. As the last epic, it also checks the initiative's Done when 4 across all five epics.

## Outcome

Claude can drive OneNote's app state when the user asks ("open that notebook", "close it", "sync it now", "show me this link", "what page am I on?"), without taking focus or changing what the user sees unasked, and without opening a way around the grants and AD-21. Every Application method has a released tool or a dated Decision.

## Requirements

- **A1 (R9) — The `AppState` pipeline.** Every `AppState` tool runs AD-7's pipeline as entry 2 sets it for this class:
  - no grant (AD-7); the write lock as entry 2 decides (Source conflict below); the 120 s deadline; a per-call timeout entry 2 sets for each method, `CloseNotebook` included, since a healthy close may outlast AD-3's 30 s default;
  - `outcomeUnknown` on the failures AD-7 step 7 lists, never retried (AD-3); entry 2 says whether a call that changes nothing, such as `get_windows`, can be `outcomeUnknown` at all;
  - path and URL arguments carry notebook and section names, so entry 2 says how they are logged (AD-13).

  `navigate_to` moves onto the pipeline and so gains its deadline, `outcomeUnknown` on a timeout, and `ComBusy` while an abandoned write is outstanding (AD-3). That changes its documented failures, so its description changes and the contract snapshot is checked (AD-14). Each tool's description says what it changes. The user-visible ones carry "user-visible" (AD-11); `open_notebook` and `close_notebook` join them if the spikes show either changes focus or the view. The skill calls every `AppState` tool only when the user asks (Assumption). (AD-7 `AppState`, AD-11)
- **A2 (R9) — `sync_hierarchy`.** `SyncHierarchy` on a notebook, section group, section or page. The result says the sync was requested, not that it finished: the call returns at once (spike 1.15) and OneNote gives no way to see a sync complete (OneMore row 23). (AD-7 `AppState`)
- **A3 (R9) — `close_notebook`.** `CloseNotebook` on a notebook ID, anything else refused before COM, with the `force` rule Q1 sets and the grant rule Q2 sets. Its result gives the notebook's name and path and warns that every ID in it changes when it reopens. It says how to reopen it: through `open_notebook` for a local notebook, and in OneNote for a cloud notebook unless entry 1 shows `OpenHierarchy` opens a URL. Grants survive, because they are keyed by path (AD-6). Entry 2 picks how the closed notebook's pages leave the search cache (AD-12). A close that OneNote holds behind a dialog is expected to end in `Timeout` with `outcomeUnknown`, to be confirmed by entry 1. (AD-7 `AppState`)
- **A4 (R9) — `open_notebook`.** `OpenHierarchy` on an existing notebook, never creating anything (`cftNone`):
  - the server makes a local path canonical first (`GetFullPath`, junctions resolved), and every check, epic 3's Q11 rule included, uses the canonical form;
  - "exists" means, for a local path, a folder that entry 2's notebook test accepts, checked under the write lock (AD-7); that test is whatever entry 1 shows is needed, because a `.onetoc2` can land minutes after a create (5.1 constraint 18) and a section-group folder holds one too;
  - a URL is accepted only if entry 1 shows `cftNone` never creates at one; the server can't check a URL's existence itself, so OneNote's refusal is the check;
  - it opens what Q3 allows, and refuses a package (epic 3's `open_package` opens those) and a missing path before COM;
  - a notebook already open returns its current ID from the hierarchy without calling COM (Assumption);
  - it gives no grant, though an existing grant for the same path applies (AD-6); what it opens follows AD-21 as Q3 and epic 3's Q11 set;
  - the result gives the notebook's ID and name, and says a cloud notebook may take about 90 s to fill (OneMore row 22). (AD-7 `AppState`, AD-21)
- **A5 (R9) — `set_filing_location`.** `SetFilingLocation`, for where Outlook items, web notes and printouts land, shipped only if Q8 keeps it; otherwise a dated Decision. (AD-7 `AppState`)
- **A6 (R9) — Windows.** A `get_windows` tool lists OneNote's windows: handle, active state, the notebook, section group, section and page each shows, and its view. Without the section's read grant, a window showing a page in a protected section reports the section and omits the page's ID (AD-21, which already withholds such pages from reads). Q5 sets whether reading the windows is user-visible, and Q4 which window changes are exposed. `navigate_to` takes an optional window. Every `Window` wrapper is released explicitly (OneMore row 10). (AD-11, AD-2, AD-21)
- **A7 (R9) — `navigate_to_url`.** A user-visible `NavigateToUrl` for the links Q6 allows, checked before COM, with the new-window rule Q7 sets for it and `navigate_to`, and the optional window from A6. A repeated call inside the window entry 12 measures gets a `userAction` to wait. OneNote reports success even for a link to a missing page, so the tool checks where it landed: entry 12 looks for a way to compare the window's current location with the link, and entry 2 writes the rule. That check reads the windows, so it needs Q5 (a) or an AD-11 exception from entry 2. Without a check, the result warns that OneNote can't confirm where it landed. (AD-11)
- **A8 (R9) — `quick_filing`.** A user-visible location picker built on `QuickFiling`, shipped only if entry 13 shows its callback works from our process and Q9 keeps it; otherwise a dated Decision. The tool call waits for the user's choice with the STA queue free, its wait doesn't count against the pipeline deadline (as for elicitation, AD-6), and it is bounded by a limit entry 2 sets and by the client cancelling the call. While a picker is open, AD-3's idle release doesn't drop the COM reference. A picker left on screen after the call ends stays until the user closes it, and its answer is dropped. The result gives the chosen ID or says the user cancelled. (AD-11, AD-3)
- **A9 (R9) — Events.** `OnHierarchyChange` and `OnNavigate` either ship as notifications the client acts on, or a dated Decision records why not (Q10).
- **A10 (R9) — Coverage.** Every `IApplication` member, slots 7 to 35 of `src/OneNoteMcp.Com/Interop/IApplication.cs`, has a released tool in one of the five epics or a dated Decision recording why it isn't exposed (the initiative's Done when 4). Entry 2 writes the table, and entry 10 checks it against the released tools.

## Done when

1. `sync_hierarchy`, `close_notebook` and `open_notebook` work against real OneNote through the `AppState` pipeline, and `navigate_to` runs on it too. A throwaway notebook closed and reopened by path keeps its grant.
2. Every tool on entry 2's amended AD-11 list says "user-visible" in its description. The skill calls them only when the user asks, and no use case calls them internally except as entry 2 allows. `get_windows` reports the page each window shows, within AD-21.
3. No `AppState` tool opens a notebook, section or file that `open_notebook`'s rules would refuse, whether directly or through a link.
4. Events ship as notifications, or a dated Decision records why they don't. Every OneNote Application member has a released tool, or a dated Decision, checked across all five epics.
5. It ships as a GitHub release through the epic 1 pipeline, with the skill and README updated.

## Boundaries

This epic owns:
- the `AppState` pipeline, and moving `navigate_to` onto it;
- `OpenHierarchy` on an existing path, `CloseNotebook`, `SyncHierarchy`, `SetFilingLocation`, `NavigateToUrl`, `QuickFiling`, `Windows` and any event sink, on the port and both gateways;
- these tools, the skill and README sections that cover them, and the initiative's coverage table.

Out of scope:
- anything that writes content;
- `OpenHierarchy` creating a section, section group or notebook (epic 5);
- `open_package` (epic 3), though this epic's `close_notebook` closes what it opened;
- starting, closing or restarting OneNote itself, which stays forbidden (AD-3).

## Notes

- **Needs Phill** (autonomous inception, 2026-11-12, revised after its Fable review the same day). Each question has options and a recommendation; the entries it touches say so.
  - **Q1 — Closing a notebook with changes OneNote can't sync yet.** `CloseNotebook` takes `force`, which closes "even if there are changes in the notebook that OneNote cannot sync before closing" (Microsoft). Options: (a) never pass `force`; if OneNote refuses or the close times out, return the error with a `userAction` to let it sync, or to close the notebook in OneNote; (b) a `force` argument that the user must confirm in an elicitation dialog naming the notebook; (c) a `force` argument with no extra check. Recommendation: (a). Losing unsynced changes is the one way this epic could lose content, and nothing in the journal would bring them back. Without `force`, a close may hang rather than refuse (see "Answered before this epic"); entry 1 probes `force=true` only if you choose (b) or (c).
  - **Q2 — Does closing or opening a notebook need a grant?** AD-7 gives `AppState` no grant. Options: (a) no grant, as AD-7 says; the descriptions say what the tools change, and the skill calls them only when the user asks; (b) `close_notebook` needs the notebook's write grant; (c) an elicitation confirmation for every close. Recommendation: (a). With `force` off (Q1), a close syncs before it closes, and grants survive because they are keyed by path. Two costs to weigh: a close stuck behind a sync jam, which no grant would prevent; and a cloud notebook the tool closes may be reopenable only in OneNote, because Microsoft documents no URL form for `OpenHierarchy` (entry 1 checks). The cost of (b): it would block closing any notebook that has no write grant, such as one the user only reads.
  - **Q3 — What `open_notebook` opens, and whether AD-21 treats it as protected.** `OpenHierarchy` opens a notebook folder, a section-group folder (as a notebook) or a `.one` section file (under Recent Opened Sections). An opened `.one` carries no `encrypted` marker, and a backup or export of a protected section is plaintext (5.1 constraint 17). Options: (a) notebooks only: a local folder that passes entry 2's notebook test, plus a OneDrive URL if entry 1 shows one opens and never creates, refusing a `.one` and a `.onepkg` before COM; epic 3's Q11 rule applies to the canonical path; (b) notebooks and `.one` section files, with every opened `.one` counting as protected under AD-21 and needing a read grant; (c) any path `OpenHierarchy` takes, with only Q11's rule. Recommendation: (a). It covers "open that notebook" and keeps loose section files, the backup and export route, out of the model's reach. Entry 2 also sets what happens to a section-group folder, from entry 1's probes.
  - **Q4 — Which window changes are exposed.** A `Window` can be activated, docked, switched to full-page view or made a quick-note window, and can navigate. Options: (a) `get_windows`, plus an optional window on `navigate_to` and `navigate_to_url`; `Active`, `DockedLocation`, `FullPageView`, `SideNote` and `SetDockedLocation` get a dated Decision not to expose them; (b) also expose each setter as a user-visible tool; (c) `get_windows` only. Recommendation: (a). Choosing the window fixes the API targeting the first window (OneMore row 14). The setters only rearrange the user's screen, and OneMore never sets them.
  - **Q5 — Is reading the windows user-visible?** AD-11 lists `Windows` as user-visible, but reading a window's current page may change nothing the user sees. Options: (a) if entry 12 shows the read changes neither focus nor the view, `get_windows` is an ordinary `AppState` read: the skill may call it when the user refers to what they're looking at ("this page", "the page I'm on"), `navigate_to_url` may use it for its landing check, and AD-11 lists only window changes as user-visible; (b) keep AD-11 as written: `get_windows` is called only when the user explicitly asks about windows, and `navigate_to_url` gets an explicit AD-11 exception for its landing check or does without one. Recommendation: (a). "Summarise the page I'm on" is the most useful thing this epic enables. It does tell the model which page is open, so the skill calls it only when the user refers to it, and a protected page's ID stays withheld without a read grant (A6).
  - **Q6 — Which links `navigate_to_url` accepts.** A `onenote:` link carries its target's path, which can be a notebook that isn't open, a loose `.one` file or a remote URL, and following it may open that target, getting around `open_notebook`'s rules and the plaintext backup route (entry 12 probes it). Any other link makes OneNote show a security dialog, then try to open it and return `hrObjectDoesNotExist` (Microsoft). Options: (a) `onenote:` links whose target lies inside a notebook that is already open, checked before COM by matching the link's path (a local path made canonical, or a cloud URL) against the open notebooks' `NotebookKey`s in AD-6's path forms; anything else refused with `InvalidArgument`; (b) `onenote:` links, where a target outside the open notebooks must also pass `open_notebook`'s rules (Q3) before the link opens it; (c) any `onenote:` link, plus OneNote web links if the desktop app opens them without a dialog; (d) any URL. Recommendation: (a). The links people follow are links between pages of their open notebooks; (b) adds a second way to open notebooks for little gain, and (c) and (d) open the routes AD-21 closes.
  - **Q7 — New windows.** `NavigateTo` and `NavigateToUrl` can open a new window. Options: (a) never: both tools pass `fNewWindow=false`, as story 1.21 decided for `navigate_to`; (b) an optional `newWindow` argument on both. Recommendation: (a). OneMore needs a 1.5 s settle after each new window, and a refused new-window request can still leave a stray window (row 24). The window argument (Q4) covers showing something in a second window.
  - **Q8 — Expose `SetFilingLocation`?** It sets where Outlook's Send to OneNote, Internet Explorer web notes and printouts land. No method reads the current setting. Options: (a) expose `set_filing_location`; the skill calls it only when the user asks, and the result says the old value can't be read or restored; (b) a dated Decision not to expose it. Recommendation: (b). It changes a lasting OneNote option that the server can't read or undo, one of its targets is Internet Explorer, and the user can set it in OneNote's options in seconds. Testing it would also overwrite Phill's own setting. If (b), entry 8 is dropped.
  - **Q9 — Build `quick_filing`?** `QuickFiling` shows OneNote's own picker for a notebook, section or page, and reports the choice through a callback object our process implements. Options: (a) build it as a user-visible location picker if entry 13 shows the callback reaches our STA thread and the wait can be bounded as A8 says; otherwise a dated Decision; (b) a dated Decision now: the model can ask where in chat. Recommendation: (a). Choosing a section from OneNote's own tree is a better answer to "where should I put this?" than typing names. OneMore receives this callback across processes, from `dllhost.exe`. A read-only registry query here (2026-11-12) shows the callback interface registered with the same type-library marshaler as `IApplication`; that it works for an STA client is untested. If (b), entry 13 skips QuickFiling and entry 9 is dropped; if the probe fails, entry 9 is dropped.
  - **Q10 — Events.** Microsoft: "Events cannot currently be added in managed code." OneMore subscribes to none and polls the current page every 1.25 s instead. In Claude Code, the only route for a server to push an event to the model is channels: a research preview, enabled per session with `--channels`, needing a development flag for a server that isn't on the allowlist. Options: (a) entry 13 probes a managed sink; if it works, ship `OnNavigate` and `OnHierarchyChange` as channel events (an extra story before entry 10); (b) entry 13 probes a sink, nothing ships, and a working sink becomes a Deferred row (for example to clear the search cache); (c) no probe: entry 2 records a dated Decision now, citing the above, with a Deferred row to revisit when channels leave the preview. Recommendation: (c). Nothing would ship either way, and `get_windows` answers "what page am I on?" when asked.
  - **Q11 — `COMAddIns` and `LanguageSettings`.** `COMAddIns` lists the COM add-ins available to OneNote. `LanguageSettings` gives access to OneNote's common language settings, and Microsoft documents nothing more. Options: (a) a dated Decision not to expose either; (b) a read-only tool listing the add-ins and whether each is loaded. Recommendation: (a). Neither helps a user work with their notes.
